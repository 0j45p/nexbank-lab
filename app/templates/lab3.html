Objective: You are logged in as Arjun Mehta (user_id: 1). Forge a JWT that identifies you as Priya Nair (user_id: 2) — using three different JWT vulnerabilities — then access her account data with the forged token.
Step 0 — Inspect Your Current JWT

A JWT is three base64url-encoded segments separated by dots: header.payload.signature. The header specifies the algorithm; the payload carries the claims (including user_id). The signature is supposed to prevent tampering — let's see if the server actually checks it.

Method A — Algorithm Confusion: alg:none

          
Flaw: Server accepts "alg":"none" — no signature required at all

        

        
⬜

      

      

        

          The JWT spec allows alg:none for unsigned tokens. A vulnerable server that accepts this
          lets an attacker set any payload — including changing user_id to another user — with
          no valid signature. The forged token ends with a trailing dot and an empty signature segment.
        


        

# Forged token structure:

base64url({"alg":"none","typ":"JWT"}) + "." +

base64url({"user_id":2,"role":"user",...}) + "." +

<empty — no signature>

Method B — Weak Secret: Forge Valid HS256 Signature

          
Flaw: Secret key is nexbank2024 — brute-forceable, found in env vars / source code

        

        
⬜

      

      

        

          The server's JWT secret (nexbank2024) is weak and exposed in docker-compose.yml
          and the /debug/config endpoint. With the secret, an attacker can craft a properly-signed
          HS256 token for any payload — including an admin or another user.
        


        

# Retrieve the secret (exposed via debug endpoint):

GET /debug/config → {"JWT_SECRET": "nexbank2024", ...}


# Sign a forged payload with that secret:

HMAC-SHA256(base64url(hdr) + "." + base64url({"user_id":2}), "nexbank2024")

Method C — Signature Verification Disabled

          
Flaw: Server decodes with verify_signature: False — any signature (even garbage) is accepted

        

        
⬜

      

      

        

          The most extreme flaw: _decode_jwt() in auth.py calls
          jwt.decode(..., options={"verify_signature": False}).
          This means the signature is completely ignored. A token with a random/wrong/empty
          signature for any payload is accepted as valid.
        


        

# In auth.py:

jwt.decode(token, secret, algorithms=[...],

           options={"verify_signature": False})
